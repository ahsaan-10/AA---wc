SECTION 1 — EXECUTIVE SUMMARY
The AI Website Fabricator is a platform that:
1. Clones any website's frontend with pixel-perfect visual fidelity using SingleFile
CLI
2. Infers the site's content structure (pricing plans, FAQs, blog posts, etc.) using a
rules-first detection engine with optional GPT-4 Vision fallback
3. Seeds a universal CMS (Content Management System) with the detected
content
4. Enables two levels of live editing:
Content editing via a universal admin panel (non-technical users)
Code editing via an integrated Monaco editor (technical users)
5. Delivers live updates — edits appear on the cloned site immediately upon
refresh

SECTION 4 — CLONE ENGINE (MAJOR UPDATE)
4.1 Why SingleFile CLI
The original M3 plan used a custom pipeline which had cascading failure modes:
CSS @import chains broke, lazy-loaded images were missed, font files were lost,
and interactive JavaScript was unnecessarily stripped. The clone looked nothing
like the original site.
SingleFile CLI solves all of these in one step. It captures the FULLY RENDERED
page in a real browser, embeds ALL resources inline, and outputs a single self-
contained HTML file.
4.2 SingleFile CLI Command

None):

Capture a pixel-perfect clone using SingleFile CLI.

browser_path: Path to Edge/Chrome executable

4.3 Multi-Page Cloning
1. Crawl Phase: Playwright visits main URL, extracts all same-domain internal links
(max 10 pages)
2. Capture Phase: SingleFile CLI captures each page independently →  one HTML
file per page
3. Link Rewriting Phase: Post-processor scans all HTML files, rewrites every
internal <a href> to point to local file (e.g., https://example.com/about →
about.html)
4. Output: A folder containing index.html, about.html, blog.html, etc. — fully
navigable locally

SECTION 5 — INFERENCE ENGINE
5.1 Inference Pipeline
1. Receive cloned HTML
2. Segment sections by scanning for semantic patterns
3. Run pattern rules (CSS class names, text content signals)
4. If rules detect 2+ sections →  skip GPT entirely (saves cost, keeps deterministic)
5. If rules detect < 2 sections →  call GPT-4 Vision with screenshot + HTML
6. Validate SiteSpec with Pydantic →  if invalid, retry once →  if still invalid, fallback
spec

5.3 Two-Layer Detection Strategy
Layer 1 — CSS Selector Rules (High Confidence): Scan for class names
containing semantic keywords: [class*="pricing"], [class*="faq"],
[class*="blog"]. Works on sites with semantic structure.
Layer 2 — Text Content Signals (Medium Confidence): Scan for content
patterns: "$" symbols near numbers →  pricing, "?" or "Q:" patterns →  FAQ, date
patterns →  blog. Works on utility-class sites (Tailwind).
5.4 GPT-4 Vision Prompt
SYSTEM: You are a backend architect. Analyze the website screenshot and
HTML.
Infer what database collections and fields are needed.
Return ONLY valid JSON:
{
"siteName": "string",
"resources": ["plans","faqs","posts",...],
"schemas": { "plans": { JSON Schema per resource } },
"bindings": [{ "slot":"pricing", "resource":"plans" }],
"hasAuth": false,
"detectedPatterns": ["saas","blog","contact"],
"fallback_mode": "full_dynamic"
}

--- PAGE 10 ---
Rules:
- Only infer from visible UI. No guessing hidden features.
- Return ONLY JSON, not prose or markdown.
- Only use resources from this allowed list: plans, faqs, posts,
team_members, testimonials, contact_submissions
5.5 Validation Rules
Model must return only JSON, not prose or markdown
Pydantic validates the top-level SiteSpec structure (field_validator filters
unknown resources)
Ajv validates JSON Schema parts for each resource
If validation fails: retry once with error appended to prompt
If still fails: create fallback spec with pages + content_blocks
System works WITHOUT OpenAI API key (rules-only detection handles test
sites)
5.6 Why This Design Reduces Trial and Error
The model is boxed into a single allowed output format. Backend does not depend
on hallucinated routes or random SQL decisions. Three layers of protection
(Pydantic →  retry →  fallback) ensure the system literally cannot crash from a bad
GPT response.

6.2 Key Design Principle
ONE TABLE FOR ALL CONTENT. Each cloned site = one project row. Each inferred
entity = one resource_key. Each content item = one row in the records table.
Actual content payload is stored in the data JSONB column.

{"name":"Pro","price":"$29","features":["Unlimited users"]}
CRITICAL DATA NESTING NOTE
Form fields live inside record.data, NOT at the record root.
CORRECT:record.data.name, record.data.price
WRONG:record.name, record.price

SECTION 9 — FRONTEND BRIDGE
9.1 How Slots Work (Updated for Static HTML)
1. SingleFile CLI generates a self-contained HTML file
2. Post-processor scans for semantic sections and injects data-fab markers: <div
data-fab="pricing">...</div>
3. fab-bridge.js script is appended to the HTML file
4. bindings.json is embedded as window.__FAB_CONFIG__ in the HTML
5. At runtime: bridge reads config →  finds nodes →  fetches records →  passes data
to renderer →  replaces static content
6. If fetch fails: original static content remains visible

SECTION 18 — FINAL CONCLUSION
The most reliable Milestone 3 architecture is not the most ambitious one. It is the
one that uses battle-tested tools (SingleFile CLI) instead of fragile custom code,
keeps the platform fixed (one Supabase schema for all sites), limits AI freedom
(rules-first with GPT only as fallback), narrows dynamic support to 6 known
patterns, offers two levels of editing (admin forms for content, Monaco editor for
HTML/CSS), and gracefully degrades when encountering complex sites.
Every major pivot made during development — switching from BeautifulSoup to
SingleFile CLI, preserving static HTML instead of converting to React, adding the
code editor, switching to Edge CDP for bot bypass — was made for a single reason:
reliability beats ambition in an academic demo context.
The innovation in this FYP is NOT building a perfect website cloner. 100% accuracy
on every live website is impossible and is not the goal. The innovation is in the
PIPELINE: a structured, AI-assisted workflow that takes any URL and produces both
a CMS-powered editable clone AND a code-level editing interface in a single
automated flow.
THE PIPELINE IS THE PRODUCT:
Clone →  Detect →  CMS →  Live Edit →  Code Editor
That pipeline — proven end-to-end across 9 development phases — is what
makes this FYP worth defending.
